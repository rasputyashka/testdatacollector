# Workload Collector

Демон для Linux: собирает системные метрики и отправляет JSON коллектору по HTTP.
Python **3.9+**, только стандартная библиотека: устанавливать пакеты через pip не нужно.
Основная цель — Debian/Ubuntu с systemd. Сборка `.deb` и TOML-парсер в эту версию не входят.

## Настройки пока в коде

В начале `workload_collector.py`:

```python
COLLECTOR_URL = "http://127.0.0.1:8080/api/v1/reports"
INTERVAL_SECONDS = 60
HTTP_TIMEOUT_SECONDS = 10
STATE_DIRECTORY = Path("/var/lib/workload-collector")
MOUNTPOINTS = ("/",)
```

`127.0.0.1` — временный адрес коллектора на той же машине. Для отдельного сервера
замените адрес и при необходимости порт/путь. Коллектор должен принимать
`POST /api/v1/reports` с `Content-Type: application/json` и возвращать HTTP 2xx.
Поддерживаются HTTP и HTTPS; для HTTPS проверяется сертификат стандартными средствами Python.
Аутентификация пока не реализована. Перенаправления HTTP не выполняются.

Для нескольких файловых систем: `MOUNTPOINTS = ("/", "/home")`.
Указывать именно точки монтирования, а не произвольные папки одной файловой системы.

Будущий парсер подключается в **`load_settings()`**: он должен вернуть `Settings`.
Остальной код получает этот объект и не зависит от способа чтения настроек.
Предполагаемый путь конфига — `/etc/workload-collector/config.toml`; сейчас файл не читается.

## Установка и управление

Сначала задайте настоящий адрес коллектора в исходнике. Из папки проекта:

```bash
sudo sh install.sh
systemctl status workload-collector.service
journalctl -u workload-collector.service -f
```

Скрипт копирует программу в `/usr/lib/workload-collector/`, юнит — в
`/etc/systemd/system/`, включает автозапуск и запускает/перезапускает службу.
После изменения исходника запустите установщик снова.

```bash
sudo systemctl stop workload-collector
sudo systemctl start workload-collector
sudo systemctl restart workload-collector
sudo systemctl disable --now workload-collector
```

Служба работает без root через `DynamicUser=yes`. systemd создаёт каталог состояния
и предоставляет службе доступ к `/var/lib/workload-collector`. На хосте он может
быть ссылкой на `/var/lib/private/workload-collector` — это штатная работа DynamicUser.
UUID не теряется после остановки службы, смены временного UID или перезагрузки.
Отдельные sysusers/tmpfiles-файлы не нужны: пользователя и каталог создаёт systemd.
Таймер `.timer` не нужен: периодический цикл уже находится внутри демона.

При подготовке `.deb` пакетный юнит обычно размещают в `/usr/lib/systemd/system/`,
а интеграцию со службой поручают debhelper. `install.sh` — ручная установка для проверки,
не скрипт сопровождения Debian-пакета.

## Проверка без отправки

На Linux можно вывести один отчёт и завершиться без HTTP:

```bash
python3 workload_collector.py --print-once --state-dir /tmp/workload-collector-demo
```

Это отдельное тестовое состояние с собственным UUID. Не запускайте от root
ручной экземпляр с каталогом состояния работающей службы.
При первом сборе `cpu.usage_percent` равен `null`: предыдущего замера ещё нет.

## Поведение демона

- Первый отчёт отправляется сразу после запуска, следующие — каждые 60 секунд.
- CPU вычисляется между последовательными сборами, в том числе после ошибки HTTP.
  100% — заняты все логические процессоры. I/O wait не считается работой CPU.
  Время гостевых CPU не прибавляется дважды. При сбросе счётчиков или смене числа
  логических CPU процент временно становится `null`.
- Расписание использует монотонные часы. Время запроса не прибавляется к каждому
  интервалу; при долгой задержке пропущенные такты не догоняются серией запросов.
- Ошибки доставки пишутся в journal. Следующая попытка — свежий отчёт на следующем
  такте. Очереди на диске и повторной доставки старых отчётов пока нет.
- Таймаут HTTP ограничивает блокирующие сетевые операции; это не абсолютный
  дедлайн всего запроса, в частности разрешение DNS может длиться дольше.
- SIGTERM/SIGINT завершают цикл. Ожидание следующего такта прерывается сразу;
  выполняющийся сетевой запрос заканчивается или получает таймаут. systemd ограничивает
  остановку 20 секундами. Неожиданное падение процесса приводит к перезапуску службы.
- Ошибка отдельного источника метрик не обнуляет показатели: соответствующий блок
  или значение становится `null`, ошибка попадает в журнал. Пустой массив означает,
  что элементов нет, а не ошибку чтения. Повреждённый `host_id` вызывает ошибку старта,
  чтобы незаметно не потерять идентичность установки.

## Формат отчёта

Пример — `example-report.json`. `sample_duration_seconds` отсутствует по договорённости.

| Поле | Смысл / источник |
| --- | --- |
| `schema_version` | Версия JSON, сейчас 1 |
| `agent_version` | Версия программы |
| `host_id` | UUID установки, создаётся один раз и сохраняется в `host_id` |
| `hostname` | Имя компьютера из `socket.gethostname()` |
| `boot_id` | `/proc/sys/kernel/random/boot_id` |
| `collected_at` | Начало сбора отчёта, UTC в ISO 8601 |
| `uptime_seconds` | `/proc/uptime`, целые секунды |
| `env` | `systemd-detect-virt`: `type` и `tech`; `unknown` при ошибке |
| `cpu` | `/proc/stat`: `logical_count` и `usage_percent` от 0 до 100 |
| `memory` | `/proc/meminfo`: `MemTotal`, `MemAvailable`, перевод KiB в байты |
| `swap` | `SwapTotal` и `SwapTotal - SwapFree`, байты; без swap — нули |
| `filesystems` | Настроенные точки монтирования: тип из `/proc/self/mountinfo`, объёмы через `statvfs` |
| `network` | `/proc/net/dev`: счётчики RX/TX по интерфейсам, кроме `lo` |

Для памяти занятость рассчитывается на коллекторе:
`100 * (total_bytes - available_bytes) / total_bytes`.

Для файловых систем `used_bytes = (f_blocks - f_bfree) * f_frsize`,
`available_bytes = f_bavail * f_frsize`: зарезервированное место не включается в доступное.

Для скорости сети коллектор сравнивает отчёты по `(host_id, interface)`:
`(новый_счётчик - старый_счётчик) / разница_времени_в_секундах`.
При смене `boot_id`, уменьшении счётчика или неположительной разнице времени
предыдущую точку нужно отбросить. Отсутствующее значение `boot_id` не означает перезагрузку.
Не суммируйте слепо трафик мостов и виртуальных интерфейсов: он может учитываться повторно.

`env` определяется при старте. При вложенной виртуализации возвращается ближайшая среда.
Текущее назначение — системные метрики на физическом Linux или в VM. Детектор умеет
обнаруживать контейнер, но CPU/RAM через `/proc` могут отражать хост, а сеть и диски —
видимую процессу среду. Потребление и лимиты контейнера через cgroups пока не реализованы.

## Проверки

```bash
python3 -m unittest discover -s tests -v
sudo systemd-analyze verify systemd/workload-collector.service
```

Проверку юнита выполняйте после установки: `ExecStart` ссылается на установленный файл.
Тесты используют временные `/proc`-фикстуры и настоящий локальный HTTP-сервер,
не обращаются к внешнему коллектору и не меняют службы системы.
